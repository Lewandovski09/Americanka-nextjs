# Архитектура данных: города, площадки, виды спорта

Миграция 043 перевела «один клуб · один город · один спорт» из хардкода в данные.
Этот файл — как устроена модель и как её расширять, не упираясь в тупики.

## Модель

```
sports ──┬──< tournament_events >── venues >── cities
         │         │  (location = venues.code)
         │         └──< tournament_categories ──< tournament_matches ──< elo_history
         ├──< user_ratings      (Ело пользователя В КОНКРЕТНОМ спорте)
         ├──< elo_history.sport_id
         ├──< avp_seasons       (сезон = спорт + опционально город)
         └──< venue_sports >── venues   (какие виды спорта принимает площадка)
```

Правила, которых держится схема:

| Факт | Где хранится (единственное место) |
|---|---|
| Город события | `venues.city_id` площадки события. У события нет своего `city_id`, чтобы оно не могло «спорить» со своей площадкой |
| Площадка события | `tournament_events.location` → FK на `venues.code` (категория площадку не копирует — колонка удаляется в 044) |
| Корты площадки | `venues.courts` |
| Вид спорта события | `tournament_events.sport_id` |
| Рейтинг игрока | `user_ratings (user_id, sport_id)`. Для основного спорта пока зеркало `users.elo` (см. ниже) |
| Сезон, куда идут очки AVP | `avp_seasons` с тем же `sport_id`; сначала сезон города площадки, иначе общий (`city_id is null`) |
| Правила формата | `lib/formats` (код). В базе — просто текст `format_kind` |
| Дивизионы (Light/Medium/Pro) и доступные форматы спорта | `lib/sports.ts` (код) |

## Рейтинг по видам спорта — переходный период

- `users.elo` по-прежнему главный источник для **основного** спорта (`beach_volleyball`).
  Триггер копирует его в `user_ratings`; прямая запись туда для основного спорта
  запрещена базой — значения не могут разойтись.
- Для **любого другого** спорта Ело пишется только в `user_ratings`.
- Весь код, который двигает рейтинг, идёт через `lib/server/ratings.ts`
  (`readRatings` / `writeRating`) — он прячет это различие.
- Следующий шаг (без правки данных): перевести чтение (рейтинг, профиль, шапка)
  на `user_ratings` с фильтром по спорту, затем развернуть зеркало и удалить `users.elo`.

## Сезоны AVP и Ело — две независимые линейки (миграция 045)

- Обе хранятся в `avp_seasons` с полем `kind` (`'avp'` или `'elo'`). У каждой линейки свой текущий сезон (`ends_on = NULL`), свой архив и своя кнопка. Закрытие одной не трогает другую.
- **AVP** (`kind = 'avp'`): очки идут в AVP-сезон, который покрывает дату события (`avp_points.season_id`). Закрытый сезон сохраняет свои очки.
- **Ело** (`kind = 'elo'`) — одно сквозное число, но у каждого Ело-сезона есть таблица `season_ratings` (`elo_start`, `elo_end`, игры, победы). При закрытии итог замораживается.
- Новый сезон: админка → «Сезони AVP» или «Сезони Ело» → «Почати новий…» (SQL-функция `start_new_season(kind, …)`). Для Ело можно выбрать: перенести рейтинг как есть или сбросить до стартового значения категории (`CATEGORY_STARTING_ELO` в `lib/elo.ts`, сброс пишется в `elo_history` с `reason = 'season_reset'`). Дата — сегодня или задним числом.
- Текущий «Сезон 2026» открыт в обеих линейках; миграция ничего не закрывает.
- Страница рейтинга: на вкладке «Рейтинг» переключаются Ело-сезоны, на вкладке «AVP» — AVP-сезоны.

## Как добавить…

### Площадку или корты
```sql
insert into venues (code, city_id, name, address, courts)
select 'arcadia', id, 'Arcadia Beach', 'Аркадія, Одеса', '{1,2,3}'
from cities where name = 'Одеса';

insert into venue_sports (venue_id, sport_id)
select id, 'beach_volleyball' from venues where code = 'arcadia';
```
Больше кортов: `update venues set courts = '{1,2,3,4,5,6,7,8}' where code = 'beach13';`
Закрыть площадку для новых событий: `update venues set is_active = false where code = '...';`

### Город
```sql
insert into cities (name, region) values ('Київ', 'Київська обл.');
```
Как только площадки есть в двух городах, в списке турниров появляется фильтр по городу,
а названия площадок получают подпись города.

### Отдельный сезон для города
(общий сезон начинайте кнопкой в админке; городской пока создаётся SQL-запросом)
```sql
insert into avp_seasons (name, starts_on, ends_on, sport_id, city_id)
select 'Київ 2026', '2026-01-01', '2026-12-31', 'beach_volleyball', id
from cities where name = 'Київ';
```
Пересечение дат запрещено только внутри одной пары (спорт, город).

### Вид спорта
1. `insert into sports (id, name) values ('padel', 'Падел');`
2. Добавить запись в `SPORTS` в `lib/sports.ts` (дивизионы, список форматов) и `'padel'` в тип `SportId`.
3. Привязать площадки через `venue_sports`.
В форме создания события появится выбор вида спорта (он скрыт, пока спорт один).

## Что сознательно отложено

- **Роли по городу** (админ только своего города). Сейчас `users.is_admin` — глобальный.
  План: таблица `staff_roles (user_id, role, city_id null, sport_id null)` + SQL-функция
  `can_manage_event(event_id)` + один серверный хелпер вместо 30 одинаковых проверок `is_admin`.
- **Город игрока** — `users.city` остаётся свободным текстом профиля (это «где живёт»,
  а не «где играет»).

## Составы матчей и названия форматов (миграция 049)

- `tournament_match_players (match_id, user_id, side A/B, position)` — кто играл в матче, с внешними ключами. Код по-прежнему пишет массивы `team_a_players / team_b_players`, а триггер `trg_matches_sync_players` синхронизирует таблицу. Несуществующего игрока в матч записать нельзя, игрока с сыгранными матчами случайно удалить нельзя.
- SQL-функции профиля возвращают `format_kind` (код формата). Название показывает приложение через `lib/formats` — переименовать формат можно в одном месте.

## Сезон в интерфейсе и скорость переходов (патч 57)

- `lib/seasons.js` — текущие клубные сезоны обеих линеек (`loadClubSeasons`, хук `useClubSeasons`). Это один запрос на вкладку браузера, общий для главной (плашка сезона вверху), рейтинга (строка «Сезон … · з …» над каждым списком), карточек Ело/AVP в профилях и `AvpSeasonCard`.
- Статистика: клубные топы и «Найбільший приріст Ело» считаются за текущий Ело-сезон. В профиле блок турниров переключается между «<сезон>» и «Весь час».
- `lib/clientCache.js` — кэш на всю вкладку браузера, переживает переходы между разделами. Сначала показываются последние данные, свежие подгружаются следом.
- `PlayerProvider` (в `app/layout.js`) загружает игрока один раз. `useCurrentPlayer()` только читает контекст.
- `middleware.js` больше не ходит в Supabase при открытии страниц (только для `/api/*`). Для редиректа на гейтед-страницах достаточно проверить, есть ли cookie сессии.
